# Implementer protocol

All six candidates are queued. Publication creates plans and delivery tracking; implementation begins only after explicit activation. Relative months start at activation. A functional public result is targeted between months 3 and 12; publishing these plans is not that result.

## Activation and capacity

Use one 16-hour weekly allocation across the owner's portfolio, including Trading Lab and any activated DL or CV project. Before activation, inspect other delivery Projects and resolve competing commitments. At most one project and one implementation issue may be In Progress. Record the selected slug and activation date in the portfolio registry. Keep issue Start date, Target date and milestone due dates blank while queued.

## Issue execution

1. Read the repository README, docs/EXECUTION_PLAN.md, stable task in planning/backlog.json and current GitHub issue. Resolve newer accepted scope before editing.
2. Verify activation, completed dependencies, milestone exit decisions and data/software rights. Work only within the approved issue boundary.
3. Create a bounded branch. Record changes to assumptions, estimates and acceptance criteria before expanding scope. Include verification and documentation in actual hours.
4. Retain exact commands, versions, seeds, configs, source hashes, resource measurements, failed runs and measured outcomes. Keep synthetic evidence separate from real-world validation.
5. Submit a reviewable PR linked to the issue. In Review requires outputs and acceptance evidence. Done requires checks, documented review and merge; decisions use a reviewed documentation PR. Disclose automated review when used.
6. For blockers, record the minimal reproduction, affected dependency and smallest next action. Keep dependent tasks Todo. Use the milestone reserve or a reviewed scope reduction; never close a task merely because it has a published plan.

## Data and evaluation

Use reproducible public data with compatible rights or deterministic synthetic generation. Manual collection, annotation and per-example curation are outside scope. Failure inspection and optional workflow feedback remain useful. Record rights for data, dependencies, models and assets independently; unknown rights block distribution and commercial-path use until resolved. Generated health records do not establish treatment dynamics. Simulation scores do not establish physical robot safety, patient benefit or business ROI.

Measure laptop feasibility before scaling: Ryzen 7 4800H, 16 GB RAM, GTX 1650 Ti 4 GB. No paid cloud, data or API is authorized. CPU fallback and bounded experiment budgets are required. Evaluate strong non-RL baselines, held-out scenarios, multiple seeds and failure cases. RL retention is conditional on useful measured behavior; a baseline-default product is an acceptable outcome.

## Product decisions

At each milestone compare actual hours and remaining reserve; record continue, reduce or stop. A useful local tool can be developed without interviews, but customer demand and operational effectiveness remain unvalidated until independently observed. No conference submission is required. Clinical deployment and physical control are outside these initial plans. No recurring tracking, external messaging, spending or product implementation is enabled by publication.

GitHub holds live delivery status. backlog.json holds stable task contracts. Synchronize scope changes by PR while preserving task IDs. Before resuming a publication operation, follow tracking instructions and reconcile remote objects and local receipts.
